# Бейзлайн поиска писем · кейс «Умный поиск в Почте»

Рабочий бейзлайн под dev-набор хакатона: 16 376 писем, 12 ящиков,
99 запросов. Без внешних зависимостей — только стандартная библиотека
Python 3.10+.

## Быстрый старт

```bash
python3 evaluate.py --data data                 # метрики + латентность
python3 evaluate.py --data data --ablation      # плюс сравнение вариантов
python3 demo.py --data data \
  --query "Найди уведомления об отклонённых платежах, полученные 29 января 2028 года." \
  --user box-... --date 2028-01-30 --k 5
python3 -m unittest discover -s tests -v        # 47 тестов
```

Отчёты пишутся в `reports/`: `dev_report.md`, `dev_metrics.json`,
`per_query_dev.csv` (по каждому запросу — recall/nDCG/MRR, число
кандидатов, латентность).

## Запуск в VS Code

Открывать нужно **папку `smartmail-baseline`**, а не родительский
каталог: пути `--data data` относительные.

1. `code smartmail-baseline` (или File → Open Folder → выбрать
   `smartmail-baseline`).
2. Если расширение Python не установлено, VS Code предложит поставить
   его из `.vscode/extensions.json` — согласиться.
3. `Ctrl+Shift+P` → **Python: Select Interpreter** → выбрать Python 3.13
   из miniconda (на этой машине `/home/alvaro-sann/miniconda3/bin/python`)
   или любой другой Python 3.10+. Внешних зависимостей нет.
4. `F5` → выбрать конфигурацию:
   - **evaluate: dev + абляция** — метрики и сравнение вариантов;
   - **evaluate: dev** — только основные метрики;
   - **demo: отклонённые платежи** — пример выдачи по одному запросу;
   - **unittest: все тесты** — 47 тестов под отладчиком.
5. Панель Testing (иконка колбы) → **Run All Tests**: конфигурация
   unittest уже прописана в `.vscode/settings.json`.
6. `Ctrl+Shift+B` — быстрый запуск `evaluate` без отладчика
   (задача из `.vscode/tasks.json`).
7. Или в интегрированном терминале (View → Terminal):

```bash
python3 evaluate.py --data data --ablation
python3 -m unittest discover -s tests -v
```

Точки останова работают в `evaluate.py`, `demo.py` и в тестах.
Если при импорте пишет `No module named smartmail`, значит открыта не
та папка: корнем workspace должен быть `smartmail-baseline`, где лежит
пакет `smartmail/`.
Если VS Code не знает тип конфигурации `debugpy` (старое расширение
Python), замените `"type": "debugpy"` на `"type": "python"` в
`.vscode/launch.json`.

## Аугментация данных

Dev-набор — 99 запросов одного шаблона «тип письма + дата». Для файнтюна
би-энкодера и проверки устойчивости к перефразировкам этого мало, поэтому
есть генератор синтетических запросов: [smartmail/augment.py](smartmail/augment.py)
и [scripts/augment.py](scripts/augment.py).

Генерируются запросы, а не письма: 16k документов достаточно для retrieval,
а синтетические письма только добавляют шум в индекс. Положительный документ
у сгенерированного запроса известен по построению.

```bash
# без сети: шаблонный fallback, проверить пайплайн
python3 scripts/augment.py --data data --out data_aug \
    --backend template --limit 300 --per-email 6

# OpenAI-совместимый API, ключ только в переменной окружения
export OPENAI_API_KEY=...
python3 scripts/augment.py --data data --out data_aug \
    --backend openai --model gpt-4o-mini --limit 2000 --per-email 5 --negatives 10

# локальная Ollama
python3 scripts/augment.py --data data --out data_aug \
    --backend ollama --model qwen2.5:7b --limit 2000
```

Результат: `data_aug/queries.jsonl`, `qrels.jsonl`, `pairs.jsonl` (с hard
negatives), `summary.json`. Каталог `data_aug/` не коммитится — это
генерируемые данные.

Проверка на аугментированном наборе:

```bash
python3 evaluate.py --data data \
    --queries data_aug/queries.jsonl --qrels data_aug/qrels.jsonl --split aug
```

Что важно понимать:

- qrels синтетические, по одному положительному на запрос, поэтому
  `Recall@10` здесь — это Hit@10 и нижняя оценка. Сравнивать с dev нельзя.
- шаблонный backend — только проверка пайплайна: запросы получаются близкими
  к теме письма и почти не проверяют пересказ смысла. Для реальной
  аугментации нужен LLM-backend.
- дедупликация идёт по тексту запроса: одинаковые формулировки из разных
  писем схлопываются, иначе метки противоречат друг другу.
- на шаблонном backend BM25 даёт R@10 ≈ 0.61 против 0.90 на dev: без даты
  и с общими формулировками письмо трудно отличить от похожих. Это аргумент
  за dense-ретривер и за более конкретные запросы от LLM.

## Как устроено

Три слоя, каждый можно заменить независимо:

1. **Метаданные — ящик и доступность.** Поиск идёт только внутри
   `synthetic_user` запроса. Письма с `doc_dt` позже `query_date`
   недоступны по условию задачи; письма с `doc_dt = null` не могут
   подтвердить попадание в конкретный день и при точном фильтре
   отбрасываются.
2. **Дата из запроса.** Парсятся «вчера», «позавчера», «сегодня»,
   «N дней/недель/месяцев назад», «29 октября 2025 года», «29 октября»,
   «29.10.2025», `2025-10-29`. Найденный фрагмент вырезается из запроса,
   чтобы дата не засоряла BM25. Дата сужает корпус до 1–262 писем.
3. **BM25 по срезу.** `k1=1.5`, `b=0.75`, IDF по всему корпусу. При
   маленьком срезе точный перебор быстрее и точнее любого ANN, поэтому
   FAISS/HNSW здесь не нужны.

Текст: NFKC, нижний регистр, `ё -> е`, снятие HTML/URL, стоп-лист.
Стеммер — Snowball Russian; сверен с эталонной реализацией
`snowballstemmer` на всех 11 290 уникальных словах корпуса (0
расхождений). Поверх стема индексируется 6-символьный префикс слова
длиннее 7 символов — страховка от того, что Snowball разводит формы
одного корня (`отклонена -> отклон`, `отклонённых -> отклонен`).
Именно этот приём поднял nDCG@10 с 0.929 до 0.963.

## Главная находка по данным

**Все 99 публичных запросов — шаблонные: «<тип письма>, полученные
<дата>».** Ни одного чисто смыслового запроса без даты в dev нет.
Поэтому публичная метрика в первую очередь измеряет качество фильтра
по дате, а не семантического поиска: `date_only` уже даёт nDCG 0.663.
На закрытом бенчмарке формулировки могут быть другими — слой
`text_only` (nDCG 0.175) показывает, что чисто лексический поиск без
даты слаб, и его нужно усиливать dense-ретривером.

Все 99 запросов имеют полное покрытие qrels фильтром «ящик + дата»,
поэтому потолок по recall не ограничен метаданными.

## Ограничения

- Смысловые запросы без даты обрабатываются BM25 по всему ящику —
  это осознанно слабое место, следующий шаг — эмбеддинги + RRF.
- Чередование согласных не лечится стеммером: «погрузка» и «погружен»
  остаются разными терминами (8 запросов из 99 не идеальны из-за этого).
- Поддержаны только точный день и относительные «N назад». Диапазоны
  («за октябрь», «с 1 по 5») и месяца целиком не парсятся.
- `doc_dt = null` (433 письма) не участвуют в поиске по конкретному дню.
- Нет сниппетов с подсветкой, пагинации, учёта тредов и дублей.

## Куда наращивать

- **Dense-ретривер** (multilingual-e5 / USER-bge-m3) по тому же срезу
  или по всему ящику, слияние с BM25 через RRF. Контракт уже готов:
  `SearchEngine.search()` возвращает `doc_id -> score`, слияние
  добавляется отдельным слоем.
- **Кросс-энкодер** на топ-40–60 кандидатов — второй по величине рычаг.
- **Разбор диапазонов дат** и мягкий буст по дате вместо жёсткого фильтра.
- **Обёртка FastAPI** с прогревом моделей на старте: p99 < 1 с считается
  вместе с сетью до браузера, но без рендера.

## Структура

```
smartmail/
  io.py        загрузка корпуса, запросов, qrels
  dates.py     разбор и вырезание даты из запроса
  text.py      нормализация, Snowball-стеммер, soft-prefix
  index.py     BM25 по подмножеству документов (global/local IDF)
  engine.py    SearchEngine: фильтры + ранжирование
  metrics.py   Recall@K, nDCG@K, MRR@K
evaluate.py    CLI-замер, абляция, отчёты
demo.py        ручная проверка одного запроса
scripts/
  augment.py   генерация синтетических запросов (template/OpenAI/Ollama)
tests/         47 тестов: даты, стеммер, метрики, фильтры, e2e, аугментация
```

Индекс собирается один раз в `SearchEngine.__init__`: токенизация
16 376 писем и построение inverted index занимают ~1.5–2 с.
